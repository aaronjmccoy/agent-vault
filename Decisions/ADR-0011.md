Given     A [[spec]]'s [[scenario|scenarios]] run as tests through [[test-step|test step]] code. A change whose tests have not run is [[hard-to-judge]], so when they run, and who sets the pace, matters.
Decide    When do the tests you've written run automatically?

Where A:  Where a project has tests, [[ci]] runs the [[test-step|test steps]] of every [[spec]] a change touches, each time a change is committed.
          → fast feedback on each change · can miss side effects on [[spec|specs]] it didn't touch
Where B:  Where a project has tests, [[ci]] runs every [[test-step|test step]], each time a change is committed.
          → catches everything · gets slower as tests grow
Where C:  Where a project has tests, [[ci]] runs every [[test-step|test step]], each time a release is prepared.
          → daily work never waits · problems surface late
Where D:  Where a project has tests, [[ci]] runs them at the pace that project sets, and the project also sets the pace at which to [[autocommit]].
          → each project chooses what fits it · there is no shared default
Combines  exclusive
Recommend D: projects differ too much for one pace.

Decision  D
