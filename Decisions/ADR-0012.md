Given     A [[spec]]'s [[scenario|scenarios]] run as tests through [[test-step|test step]] code. A change whose tests have not run is [[hard-to-judge]], so when they run, and who sets the pace, matters.
Decide    When do the tests you've written run automatically?

Where A:  When a change is committed, [[ci]] runs the [[test-step|test steps]] of every [[spec]] the change touches.
          → fast feedback on each change · can miss side effects on [[spec|specs]] it didn't touch
Where B:  When a change is committed, [[ci]] runs every [[test-step|test step]].
          → catches everything · gets slower as tests grow
Where C:  When a release is prepared, [[ci]] runs every [[test-step|test step]].
          → daily work never waits · problems surface late
Where D:  Where a project sets a test pace, [[ci]] runs that project's tests at that pace, and the project also sets the pace at which to [[autocommit]].
          → each project chooses what fits it · there is no shared default
Combines  exclusive
Recommend D: projects differ too much for one pace.

Consequences
- When defining [[ci]], the [[term]] note says it is the automated checker that runs a project's tests at the pace that project sets ([[ADR-0012-v2]]).
- Where the cheat sheet explains checks, it says that each project sets the pace at which [[ci]] runs its tests and the pace at which to [[autocommit]] ([[ADR-0012-v3]]).

Decision  D
